Harness 正在成为模型之外的能力层

从模型调用走向状态、权限、验证与可恢复执行，Agent 系统的竞争边界正在持续外移。

Four signals

  • Harness 成为系统层

    模型能力越来越容易替换，执行环境、上下文管理和验证闭环开始决定任务完成率。

  • Verification 优先

    Coding Agent 的价值从生成代码，转向运行、验证、修复并提供可审阅的完成证据。

  • MCP 回归能力边界

    MCP 更适合作为发现、授权与跨边界调用协议，而不是替代所有 CLI 和 API。

  • 内容与展示解耦

    AI 只生成结构化内容，固定 Schema、Astro 和 Slidev 负责一致的阅读与演示体验。

Agent Runtime 不再只是 Tool Loop

Runtime 正在统一管理模型、工具、状态、权限、环境、恢复和审计。

  • 长任务需要可持久化状态和可恢复执行，而不是只保存消息列表。
  • 工具调用必须进入权限、沙箱和审计边界。

限制：不同 Harness 对 Session、Memory 和 Tool 的定义仍未统一。

Schema 比 Prompt 更适合约束内容结构

Prompt 负责内容质量，Schema 负责字段、数量、URL 和枚举的确定性约束。

  • Daily Brief 固定四个 signals，并限制 sections 和 actions 数量。
  • 构建前验证可阻止缺失来源或非法布局进入生产页面。

限制：Schema 无法替代事实核验与编辑判断。

同一内容应同时生成阅读版和演示版

Astro 面向搜索、手机和归档，Slidev 面向逐页分享和全屏演示。

  • 两种输出共享事实、判断、Topic 和 References。
  • UI 实现彼此独立，避免 Astro 与 Slidev Runtime 直接耦合。

限制：阅读密度和演示密度需要通过字段分层协调。

RSS 同时承担发现入口和订阅出口

RSS 输入形成候选发现流程，RSS 输出让全部已发布内容进入标准阅读器。

  • 聚合摘要只能用于发现，最终判断必须回查一手来源。
  • Astro 可在静态构建时生成标准 RSS endpoint。

限制：RSS 不适合承载所有交互式演示内容。

GitHub Pages 应发布构建产物而不是手写 HTML

GitHub Actions 统一构建 Astro、Slidev 并组装单一 Pages Artifact。

  • 构建产物不再由 AI 或人工直接维护。
  • 当前生产站在原型验证完成前保持不变。

限制：切换 Pages Source 需要独立迁移和回滚方案。

From signals to action

  • 跑通第一条 Vertical Slice

    使用同一份 Brief 生成 Astro 阅读版、Slidev 演示版与 RSS 条目。

  • 固定自动内容权限边界

    Scheduled Agent 只允许修改 content 下的受控目录。

  • 保留现有 Pages 生产站

    原型 CI 只上传构建 Artifact，不切换公开站点。

  • 用真实构建结果修正规划

    根据 Astro 和 Slidev CI 日志更新 Schema、路径和组装策略。
