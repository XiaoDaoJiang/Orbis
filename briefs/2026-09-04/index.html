Agent 能力上升后，运行时边界正在从调用工具转向治理与可中断执行

GPT-6 Astra 把高能力模型带入更严格的安全门控，MCP 无状态化推动远程部署简化，而 Registry、Session 与 Approval 正在成为 Agent Harness 的核心工程边界。

Four signals

  • 高能力模型开始强迫 Runtime 显式治理

    Astra 达到 Critical cybersecurity capability 后，隔离、监控、授权和自动中断不再只是安全附加项，而是高能力 Agent 的运行前提。

  • MCP 正从会话协议转向无状态远程调用边界

    新版 MCP 去除核心会话依赖后，水平扩展、负载均衡与故障恢复更接近普通无状态服务，但身份与授权需要重新设计。

  • Registry 正在补上 Agent 生态的发现与审批层

    AWS Agent Registry 把 Agent、MCP Server、Skill 等资源统一进入可发现、可审批、可授权的目录，治理面开始独立于执行面。

  • Harness 竞争开始落到 Session、Skill 与 Approval 体验

    OpenClaw 2026.9.1 把持久审批、个人 Skill Library、Session 恢复和多端工作区作为核心能力，说明 Harness 正在产品化运行时状态。

Astra 把安全边界推入 Agent Runtime

当模型本身具备更强的自主网络与代码能力，最小权限、隔离环境、轨迹监控和可中断执行必须成为 Runtime 的默认结构。

  • OpenAI 在 2026-09-03 发布 GPT-6 Astra，并将其评估为首个达到 Critical cybersecurity capability 阈值的广泛部署模型。
  • OpenAI 描述了更严格的隔离、模型权重保护、全轨迹监控以及对潜在未授权行为的自动停止机制。
  • Astra 面向高风险网络安全任务仍采用更严格的访问分层，默认产品配置并不等同于评测中的最高权限环境。

限制：相关能力与安全结论主要来自 OpenAI 自身评测和系统卡，仍需要第三方长期复现与生产事故数据。；更强监控可能中断合法任务，因此 Runtime 还需要清晰的人工接管和恢复语义。

能力提升与可监控性不再同步增长

评测分数继续提升并不代表 Agent 更容易监督，工程系统必须把可观测、权限和停止条件作为独立指标。

  • OpenAI 报告 Astra 在 ExploitBench 上达到 100%，并在内部近期漏洞集上展示了更高的任意代码执行能力。
  • OpenAI 同时表示 Astra 的书面推理在部分测试中比 GPT-5.6 Sol 更难监控，因此增强了生产侧的 misalignment monitoring。
  • 这意味着单纯依赖模型自述或最终答案不足以判断执行是否仍处于授权范围。

限制：benchmark 结果不能直接外推到所有真实网络和软件环境。；监控器本身也可能产生漏报、误报和策略绕过，需要独立评估。

MCP 无状态化让远程 Server 更像标准服务

去掉核心会话依赖后，MCP Server 更容易水平扩展，但客户端身份、授权上下文和长任务状态必须被显式外置。

  • AWS 在 2026-09-02 的架构文章中指出新版 MCP 核心已转向无状态，并移除了 initialize 握手和 Mcp-Session-Id 依赖。
  • 每个请求携带自身协议版本和客户端上下文，使负载均衡器不再必须维持会话黏性。
  • 长任务、用户授权和业务状态仍然存在，只是不能再默认寄托在协议级 Session 上。

限制：旧客户端和旧 Server 的迁移窗口仍可能要求兼容层。；无状态协议并不会自动解决凭证传递、租户隔离和长任务恢复问题。

Agent Registry 开始成为治理控制面

当 Agent、MCP Server 和 Skill 数量增长，发现、审批、版本和授权需要独立目录，而不能继续散落在 Prompt 与手工配置中。

  • AWS Agent Registry 的 Registry Record 可以表示 Agent、Tool、Skill 或自定义资源。
  • Registry 支持从 MCP Server 或 A2A Endpoint 同步元数据，也支持人工创建记录。
  • Registry 可以设置记录审批策略，并通过 MCP-compatible endpoint 暴露受控的发现能力。

限制：Registry 解决的是发现与治理，不替代 Runtime 的执行隔离、凭证最小权限和任务审计。；当前实现仍具有云厂商特定的 IAM、命名空间与迁移约束。

Harness 正把运行时状态做成可见产品能力

OpenClaw 的最新发布显示，Session、Skill、Approval、恢复和多端交互正在从内部实现细节变成用户直接依赖的工作流契约。

  • OpenClaw v2026.9.1 于 2026-09-03 发布，并加入个人 Skill Library、跨共享 Gateway 的身份化 Skill 管理与更完整的 Session 工作区。
  • 对 OpenClaw 配置的 MCP Server，Codex 的 Allow Always 审批可持久化，并跟随 Session posture 复用。
  • 委派系统 Agent 发起配置变更或 Gateway 重启时，Approval Card 会回到发起会话，而不是静默阻塞后台任务。

限制：OpenClaw 的实现代表一个高活跃开源 Harness 的产品选择，不应直接视为行业标准。；持久审批会提高便利性，也要求更清晰的作用域、撤销和审计机制。

From signals to action

  • 审计 MCP Session 假设

    列出当前 Client、Server、Gateway 对 initialize、Session ID、黏性路由和长任务状态的依赖，并制定无状态迁移测试。

  • 给高权限 Agent 增加可中断边界

    将网络、文件、Shell 和凭证访问纳入最小权限策略，并为高风险动作增加轨迹监控、自动停止和人工恢复入口。

  • 建立 Agent 资源目录原型

    用最小 Registry 记录 Agent、MCP Server、Skill、版本、Owner、审批状态和可用环境，验证发现与授权是否能从 Prompt 中移出。

  • 测试持久审批的作用域

    对 Allow Always 类能力验证身份、Session、Server、Tool 参数范围、撤销和审计日志，避免便利性扩大权限面。
