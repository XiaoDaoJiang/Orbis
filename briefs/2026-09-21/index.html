Agent 执行栈正在分出快慢路径：专用决策器、真实任务评测与并发 Runtime 同时成熟

CUA-S1 把 GUI 表单决策压缩成小型 one-pass 模型，Android Bench 开始同时评测模型、Agent 架构与工具调用合同；Realtime-Venus 则用双循环把实时交互和后台任务拆开。与此同时，Grok Voice Transcribe 2.0 把 turn detection 等语音控制能力下沉到输入层，Xing4.0-29B-A4B 则把 Agent 规划、工具调用与推理 Runtime 适配直接写进模型发布。Agent 工程正在从“一个大模型包办全部步骤”转向快路径、慢路径、评测与运行时协同的分层系统。

Four signals

  • 高频界面决策开始从通用 LLM 下沉到专用 System One 模型

    cua-s1-forms 不生成文本，而是一次前向为表单元素的候选动作打分，显示 Agent 热路径可以用小型专用模型承担低延迟、边界明确的判断。

  • Agent Benchmark 正从裸模型比较升级为 Model × Harness × Tool Contract

    Android Bench 采用 Harbor、mini-swe-agent v2 原生工具调用，并新增 specialized agent 与 long-horizon 结果，使评测对象更接近真实软件工程 Agent 系统。

  • 实时 Agent Runtime 正把对话循环与后台执行循环分离

    Realtime-Venus 让一个循环持续处理语音和视觉交互，另一个循环异步执行委派任务并把结果送回同一会话，避免长任务阻塞实时交互。

  • 模型可用性越来越取决于输入基础设施与推理 Runtime 是否同步就绪

    Grok Voice Transcribe 2.0 把 streaming、turn detection、diarization 等能力做成语音 Agent 输入原语；Xing4.0 则在模型发布时同时面对多种推理框架适配尚未合并的现实。

Computer Use 的高频决策可以从通用生成模型拆成专用快路径

当动作空间有限、目标可枚举时，用小型分类式模型先完成低延迟决策，再把复杂规划留给通用 Agent，可以降低每一步都调用大模型的成本与等待时间；但安全边界仍必须由 Runtime 独立执行。

  • cua-s1-forms 是面向 GUI 表单填写的 one-pass option scorer；它不生成文本，而是针对每个 UI 元素和候选动作输出概率，并可将多个元素在一个 batch 中并行评分。证据：cua-s1-forms Model Card
  • 该 checkpoint 的模型卡给出 706,048 个可训练参数和约 2.8 MB checkpoint，并说明训练使用 10,000 个合成 episode；模型卡报告 form-disjoint synthetic test top-1 为 99.95%，真实 demo eval 为 196 个决策。证据：cua-s1-forms Model Card
  • Cua-S1 仓库把 planning 与 execution 分离，默认 dry run，并要求单一明确目标窗口、snapshot-bound element token、变更后重新观察；execute 与 submit 需要分别显式开启。证据：Cua-S1 Repository README

限制：模型卡明确说明真实评测只有 196 个决策，且尚未在任意真实世界表单上验证，不能把 demo 结果外推为通用 computer-use 能力。；Cua-S1 仓库将 checkpoint 输出视为决策建议而不是授权边界，实际执行仍需要最小权限、独立验证与人工确认机制。

软件工程评测开始把 Harness、工具协议和任务时长纳入同一实验

当不同 Agent 使用不同工具调用方式、系统提示和执行环境时，只比较基础模型分数会遗漏关键变量；可复现评测需要把模型、Harness、工具接口和任务集一起版本化。

  • Android Bench 1.0 包含 100 个任务，来自 38,989 个开源 Android pull request 的候选池，并以真实 issue 与已合并修复为基础构造软件工程任务。证据：Android Bench 1.0 Methodology
  • Android Bench 已将执行标准化到 Harbor，并在 mini-swe-agent v2 中要求模型通过 provider API 的原生 bash tool 调用执行命令，而不是输出 Markdown shell 代码块。证据：Android Bench 1.0 Methodology
  • Android Bench 在 2026-09-17 的 changelog 中新增 long-horizon tasks，并开始发布 specialized agents 的结果，包括 antigravity-sdk、pi 与 codex。证据：Android Bench Changelog

限制：Android Bench 聚焦 Android 工程且任务分布有明确筛选标准，结果不能直接代表所有语言、仓库或企业内部代码库。；其成本与延迟指标包含 provider 网络与当时价格，官方也提醒失败较早的模型可能因为少执行步骤而显得更便宜或更快。

实时 Agent 需要把“继续交互”和“后台执行”变成两个并发循环

语音和视觉 Agent 如果把工具执行塞进单一对话循环，长任务会直接阻塞用户体验；双循环 Runtime 允许感知与说话继续进行，同时把耗时工作交给异步 Harness。

  • Realtime-Venus 由 9B 的 Omni、9B 的 Audio 和 Realtime-Venus-Harness 三部分组成；Harness 负责捕获委派请求、执行后台工作并把结果返回原会话。证据：Realtime-Venus Repository
  • Realtime-Venus 的设计允许模型在持续接收音视频输入和生成语音时，把自然语言任务异步委派给 Harness，后台任务完成后再由同一会话安排结果的口语化交付。证据：Realtime-Venus Repository
  • 项目页面将系统描述为两个共享同一会话的循环：一个负责实时感知与语音，另一个负责委派任务与回复准备。证据：Realtime-Venus Project Page

限制：项目公开结果主要来自作者论文与项目方测试，仍需要在不同硬件、网络和真实工具链中复现实测。；在线 demo 对 GPU 和本地模型服务有较高要求，持续全双工体验的资源成本不能仅从模型参数量判断。

Speech-to-Text 正从转写组件变成 Voice Agent 的控制输入层

当转写服务直接提供 streaming、speaker、关键词和 turn-end 信号时，语音 Agent 的 Runtime 可以把更多会话状态判断建立在结构化输入事件上，而不是在文本生成之后补救。

  • Grok Voice Transcribe 2.0 支持 batch 与 streaming 转写，并提供 word-level timestamps、speaker diarization、最多 8 个独立 channel、最多 100 个 key terms 和 smart turn detection。证据：Introducing Grok Voice Transcribe 2.0
  • xAI 表示该模型可自动检测语言、支持数十种语言并在一次录音中跟随语言切换；其官方 short-phrase 测试中 WER 从上一代的 20.6% 降至 6.8%。证据：Introducing Grok Voice Transcribe 2.0
  • 官方定价保持 batch 每小时 0.10 美元、streaming 每小时 0.20 美元，并表示 2.0 将成为 Speech-to-Text API 默认模型，1.0 会在之后数周逐步弃用。证据：Introducing Grok Voice Transcribe 2.0

限制：准确率和 WER 数字来自 xAI 自有评测，应视为厂商报告而不是独立 benchmark 结论。；更准确的转写和 turn detection 仍不能替代业务层授权、幂等、敏感数据处理与操作确认。

Agent 模型发布正在把推理框架适配本身暴露为交付条件

Agent 能力不仅由权重决定；长上下文、tool parser、reasoning parser、speculative decoding 和 serving framework 的实现状态会直接影响模型是否能进入真实 Harness。

  • Xing4.0-29B-A4B 采用 29B 总参数、每 token 激活 4B 的 MoE 结构，原生支持 256K context，并将 mHC、MLA 与 MTP 组合描述为面向多步规划、工具调用和复杂推理链的 Agent-oriented architecture。证据：Xing4.0-29B-A4B Repository
  • 项目方报告 Xing4.0-29B-A4B 在 SWE-bench Verified、Terminal-Bench 2.1、Claw-Eval 与 Tau3-Bench 上分别取得 75.0、57.5、76.55 与 64.63；这些数字均来自模型发布方给出的评测。证据：Xing4.0-29B-A4B Repository
  • Xing4.0 仓库说明 SGLang、vLLM、TensorRT-LLM、llama.cpp 与 KTransformers 的原生支持 PR 在发布时仍处于 pending，需要使用对应 PR branch 才能启用完整支持。证据：Xing4.0-29B-A4B Repository

限制：Benchmark 结果属于模型发布方自报，应结合独立复现和目标仓库任务再判断真实收益。；推理框架的 pending 适配意味着即使权重已开放，生产 Runtime 仍可能需要自定义分支和额外兼容验证。

From signals to action

  • 为 Agent 热路径拆出可替换的快决策层

    找出枚举动作、分类、路由和字段匹配等高频步骤，用小模型或规则实现 fast path，并把复杂规划和异常回退保留给通用 Agent。

  • 把 Benchmark 配置与模型版本一起锁定

    记录 Harness、system instructions、tool schema、任务集、provider endpoint 和运行资源，避免把执行环境变化误判成模型能力变化。

  • 对实时 Agent 建立前台与后台两个状态机

    将 listen/speak 与 delegate/work/deliver 分开建模，明确打断、取消、结果回送和已经播放确认等状态。

  • 新模型接入先跑 Runtime compatibility gate

    在比较模型质量前先验证 tool calling、reasoning parser、长上下文、并发和目标 serving framework，未通过兼容门禁就不要进入生产评测。
