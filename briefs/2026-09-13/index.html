Agent 配置进入可测试时代，运行时漂移必须纳入回归门禁

从 Claude Code 把 plugin eval 变成可重复评分工件，到 GPT-6 Astra 对 Skills 与 AGENTS.md 更敏感，再到 Kimi Code 在不改变模型 ID 的情况下切换底层模型，以及 Cognition Fusion 用双 Agent Harness 优化单任务经济性，Agent 工程正在面对一个更具体的问题：配置、模型别名和 Harness 本身都会漂移，必须像代码一样被版本化、评测和治理。

Four signals

  • Plugin 与 Skill 开始拥有原生回归测试入口

    Claude Code v2.1.269 新增 claude plugin eval，可运行插件评测套件并产出可重复评分与 JSON、HTML 报告，Agent 扩展从人工试用开始进入机器可比较的质量门禁。

  • AGENTS 与 Skills 已成为真实运行时配置

    OpenAI 明确提醒 GPT-6 Astra 更容易受 Skills 和 AGENTS.md 等文件中的指令影响，并建议审计这些文件；模型升级时，提示与项目规则本身需要进入回归测试矩阵。

  • 稳定模型 ID 不再等于稳定行为

    Kimi Code 将 K2.8 Preview 全量切到既有 kimi-for-coding 模型 ID，客户端无需改配置即可获得不同能力与推理设置，说明别名升级必须纳入版本溯源与行为回归。

  • Harness 正直接优化每个任务的经济性

    Cognition Fusion 让 frontier lead 与低成本 sidekick 保持独立上下文并协作完成任务，目标不再只是按请求路由模型，而是从整条 Agent 执行链优化质量与单任务成本。

Agent 扩展开始拥有可重复的质量门禁

当 Skill、Plugin 和命令成为 Agent 行为的一部分时，仅靠人工试跑不足以支撑持续升级；评测套件、稳定输入、评分结果和可审阅报告需要像测试工件一样进入发布链。

  • Anthropic 在 Claude Code v2.1.269 中新增 claude plugin eval，用于针对 Claude Code 运行插件自己的 eval suite。证据：Claude Code v2.1.269
  • 该命令会输出带评分的可重复结果，并提供 JSON 与 HTML 报告，官方 release notes 将其作为插件评测能力发布。证据：Claude Code v2.1.269
  • Claude Code v2.1.269 于 2026-09-11 发布，随后 2026-09-12 已有 v2.1.270，说明扩展能力与宿主版本都在快速迭代。证据：Claude Code v2.1.269

限制：plugin eval 能提供可重复评分，但评测质量仍取决于测试样本、grader 与成功标准是否覆盖真实使用场景。；Claude Code 的宿主版本仍在快速更新，单次通过不能替代跨版本持续回归。

Skills 与 AGENTS 文件需要按运行时配置治理

更强的 instruction following 会放大项目级规则文件的作用；模型升级不只是替换 model name，还应同时重新验证 Skills、AGENTS、delegation 策略和测试边界。

  • OpenAI 的 GPT-6 Astra 指南说明，该模型比此前模型更强地遵循指令，也可能更敏感于 Skills 和 AGENTS.md 等可访问文件中的指令，并明确建议审计这些文件。证据：OpenAI GPT-6 Astra model guidance
  • OpenAI 指南指出 GPT-6 Astra 在部分工作流中可能比预期更少委派子 Agent，应用应明确指定何时以及以多大程度使用 subagents。证据：OpenAI GPT-6 Astra model guidance
  • OpenAI 指南指出 GPT-6 Astra 在编码任务中倾向于进行充分测试，小任务可能执行超出必要范围的测试，因此应按任务规模校准验证要求。证据：OpenAI GPT-6 Astra model guidance

限制：这些行为建议针对 GPT-6 Astra，不能直接假设其他模型具有相同的 instruction sensitivity 或 delegation 偏好。；审计规则文件只能降低配置漂移风险，仍需真实任务 eval 才能判断组合后的 Agent 行为。

模型别名可以保持不变，但行为与成本边界会改变

当供应商在不改变客户端配置的情况下升级别名背后的模型时，生产系统必须记录实际模型版本、发布窗口和评测结果，否则同一配置无法保证同一行为。

  • Kimi Code 于 2026-09-11 宣布 K2.8 Preview 已全量上线，同时保持模型 ID 为 kimi-for-coding，因此客户端与第三方工具无需修改配置。证据：Kimi Code K2.8 Preview
  • K2.8 Preview 提供 low、high、max 三档 thinking level，默认 max；关闭 thinking 时，相关请求由 K2.8 Preview 的 no-thinking 模式处理。证据：Kimi Code K2.8 Preview
  • Kimi Code 文档说明 K2.8 Preview 提供最高 1M context window，并向所有会员层级开放。证据：Kimi Code K2.8 Preview

限制：Kimi 对能力提升和推理效率的描述属于厂商自报，不应直接当作跨供应商 benchmark 结论。；稳定别名简化了客户端升级，但也意味着调用方需要自行建立 resolved-version 与行为回归的可观测性。

双 Agent Harness 把模型选择变成持续协作结构

任务级成本优化正在从一次性的模型路由转向长期保持上下文的多模型协作；真正需要评测的是 lead、sidekick、委派协议与缓存策略组成的整体系统。

  • Cognition Fusion 同时运行两个拥有各自持久上下文和工具的 Agent，由 frontier lead 负责会话并把工作委派给更低成本的 sidekick。证据：Introducing Fusion in Devin Desktop and CLI
  • Fusion 中 lead 负责计划、歧义解释与最终 review，sidekick 负责代码探索、实现、测试并汇报结果；lead 可以在 sidekick 无法处理时重新接管。证据：Introducing Fusion in Devin Desktop and CLI
  • Fusion 不在模型之间传递完整对话，而只交换 brief、结果和反馈，让两个 Agent 各自建立持久上下文并利用 prompt caching。证据：Introducing Fusion in Devin Desktop and CLI
  • Cognition 报告 Fusion 在多项 coding benchmarks 上相较其他 model harness 最多提升 39% 的效率，并主张应按 price per task 而不是 price per token 评价模型与 Harness 组合。证据：Introducing Fusion in Devin Desktop and CLI

限制：39% 效率提升来自 Cognition 官方及其合作评测，属于厂商自报结果，不代表所有代码库与任务都能复现。；双 Agent 长驻上下文会增加编排复杂度，收益依赖任务能否被稳定拆分以及 lead 的 review 是否足够可靠。

长期 Agent 的状态层需要集中控制与可预测接口

Agent 一旦长期运行并持续读取设置、会话与业务状态，数据层就不只是存储问题；集中授权、审计、限流和可预测请求成本能够把状态基础设施变成真正的控制面。

  • OpenAI 报告其 Habitat 在线存储平台当前每秒处理超过 7000 万请求，支撑每周超过 10 亿用户使用的产品，并管理超过 500 PB 数据。证据：Rapidly scaling online storage to serve over 1 billion ChatGPT users
  • OpenAI 将 Habitat 从客户端库拆成独立服务，以建立部署、可观测性与平台改进的单一控制点，并集中执行访问控制、审计日志和底层存储访问限制。证据：Rapidly scaling online storage to serve over 1 billion ChatGPT users
  • Habitat 刻意使用受限 NoSQL API 来保持请求成本可预测，避免任意 SQL 带来的大扫描和不可控 fanout，并把复杂查询隔离到独立的辅助分析视图。证据：Rapidly scaling online storage to serve over 1 billion ChatGPT users
  • Habitat 使用 Envoy 聚合连接并通过 HTTP/2 multiplexing、rate limits 与 circuit breakers 降低大量进程对下游资源造成 thundering herd 的风险。证据：Rapidly scaling online storage to serve over 1 billion ChatGPT users

限制：Habitat 的规模与实现来自 OpenAI 官方工程文章，不能直接外推为所有 Agent 产品都需要同样的分布式架构。；集中控制点会改善治理一致性，但也会成为关键基础设施，需要独立的高可用、隔离和容量设计。

From signals to action

  • 给每个 Skill 与 Plugin 建立行为回归套件

    为关键扩展维护稳定任务集、grader、预期副作用和失败样本，并在宿主 Agent 或模型升级时自动重跑，而不是只验证能否加载。

  • 记录实际模型版本与 Harness provenance

    在每次 Agent run 中记录模型别名、可解析的底层版本、Harness 版本、规则文件版本和关键配置，使同一任务结果能够跨升级比较。

  • 用 price per task 评估多模型协作

    对 lead 与 sidekick 组合同时记录成功率、总成本、工具轮次、缓存命中和返工次数，再决定是否优于单模型或简单路由。

  • 把状态访问约束放到独立控制面

    为长期 Agent 的状态与业务数据提供集中授权、审计、限流、熔断和有界查询接口，避免把资源保护只留给调用端自律。
